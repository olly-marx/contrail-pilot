## What can change with NO game change and no hook (pure test edits)
1. **Replace each fixed wait that precedes a state check with the condition itself** (`waitForFunction`/`isVisible` poll with `evaluate`, never an async predicate). Floor saving = most of the fixed-ms column: ~13.8 + 11.1 + 10.0 + 20.2 = 55 s of idle time in the four files, more under load (a fixed wait is the SAME length at load 30, a condition returns at once). This is the safe, no-rule-touching 20% of the 870 s.
2. **The 3.2 s / 2.5 s results reveal**: a real tap on the card skips it for a player; the test can tap (a real tap) then wait for `#againBtn`.
3. **Parallelise by file, not by time**: the five run in the same BJOBS=3 pool; they are the long tail of the pool (the rest are 40-70 s), so splitting `postrails` (8 flights) into two halves of 4 flights cuts the tail from 306 s to ~160 s with zero change to what is asserted. (Needs the saved state between halves to be declared in a fixture: the test already reloads a fresh page per flight.)

## The user's rule (2026-10-27): the walkthrough/rails tests use REAL taps, no skips or hooks
Checked in the code, because the rule is stated as a fact and I read the files: **`walkthrough` already breaks it today.** Its `fly()` sets `s.graceUntil = 1e12`, replaces `s.hitsStorm` and `s.hitBird` with `() => false`, moves the next airport 1e7 px away, calls `s.applyFlap()` directly, zeroes `s.heat` every tick, and ends the flight with `s.finish({ landed: true })` after patching the result fields (l.36-43). It tests the screens AFTER a flight (lessons, claims, the hangar lead), not the flight. `onrails` and `postrails` do fly with real mouse events (their `look()` reads game state, their taps are `p.mouse.click`).

## A declared game-clock source (proposal, for the Coordinator to decide; nothing built)
- **What it is:** a test-only declared time scale, `window.__CP_TIMESCALE = k` set by `addInitScript` in a shared test helper (a `tests/lib/` change = ALL tests, so the helper is one reviewed commit), read once in `GameScene.update` to multiply `dt` (and the takeoff hold timer). Production never sets it; with it unset the code path is byte-identical (a constant 1). It is a GAME change of one line, declared, not a hidden hook.
- **What it replaces:** the wall-clock length of a flight and of the takeoff hold. **Every tap stays a real `mouse.down/click` event; no state is poked.** What it does NOT replace: the pilot's reaction time (45 ms real = k x 45 ms of game time), so k is capped by the bot: at k = 2-3 the bot is as good as a child; at k = 6 it will miss gaps. Honest expectation: flights 2-3x shorter, i.e. postrails ~306 -> ~130 s, onrails ~150 -> ~80 s, NOT "seconds". Seconds-long needs the Node route (the sim engine, which already runs these rules without a browser), keeping only a SHORT real-tap check per screen.
- **Defect classes these tests caught (the plants must still FAIL at k = 3):** onrails: the turbulence gate open before lesson L2 (`gapTurb` in src/upgrades.js), a teaching strip covering the plane, a rails step with more than one tappable target; rails2: a target scrolled out of view, the parcels step with no tappable price; postrails: a toast stacked over a strip for 3+ frames, lesson L5 stalled by an unclaimed prize (retired by R8), the hub NEXT leading to a dead end, L3-L5 not done by flight 10; walkthrough: wild animals allowed before the NATURE lesson, the free part not offered after flight school, the CLAIM flow. Each has a plant in `tools/plants.tsv`; the proof of the stepper is those SAME plants failing with `__CP_TIMESCALE=3`.
- **Risk:** a timing-sensitive defect (a frame hitch, a late-loading picture) is shortened to k-times less wall time; keep one unscaled run of `onrails` in CI (not in the local gate) as the real-time control.

## Order proposed
(1) pure test edits 1+2 (no rule touched; plants unchanged); (2) one measuring slot (~15 min): a per-test timeline, flight vs wait vs load; (3) decide the declared time source from those numbers, not from this estimate; (4) the `postrails` split.
